\section{Assigned Project and Scope}
The project is a campus marketplace where SLU students can buy and sell items such as textbooks,
electronics, and furniture. Sellers can create listings with an AI-generated description, and buyers
can search for items and get personalized recommendations. The two main course topics covered
are server-side Web APIs with databases (FastAPI, MySQL, JWT) and keeping inventory correct
when two buyers try to reserve the same item at the same time.

\textbf{Exclusions:} real payment processing, mobile app, seller analytics.

\section{Architecture and Technology Decisions}
\begin{figure}[H]
  \centering
  \diagram{architech.jpeg}{0.6}
  \caption{System architecture. The React frontend runs in the user's browser and calls the FastAPI backend over HTTPS (REST/JSON with a JWT). All backend modules run in one FastAPI application, which reads and writes MySQL over SQL, calls the external LLM API over HTTPS, and uses Redis for cache lookups only if time permits (dashed).}
\end{figure}

\textbf{Tracing a reservation.} When a buyer clicks \emph{Reserve}, the browser sends
\texttt{POST /reservations} with the listing ID and JWT. FastAPI verifies the token, reads the
listing's quantity and version, and runs one conditional update that decrements quantity and
increments version only if the version is unchanged. If the update affects one row, the API inserts a
pending reservation with \texttt{expires\_at} set 15 minutes ahead and returns 201; if it affects zero
rows, another buyer won the race and the API returns 409. The React page then shows the
reservation or a ``no longer available'' message.

\begin{figure}[H]
  \centering
  \diagram{datamodel.jpeg}{0.6}
  \caption{Data model. Arrows show one-to-many relationships: a user sells many listings and makes many reservations, a category contains many listings, and each listing can have many reservations. \texttt{Users\_views} and \texttt{Users\_saves} record which listings a user viewed or saved; they are the input to the recommendation module. \texttt{Listing.version} is the integer used by the reservation update to detect conflicting requests, and a unique constraint on (buyer, listing) prevents a buyer from reserving the same listing twice.}
\end{figure}

\textbf{Technology choices.} React 18~[3] fits a marketplace UI built from reusable product cards,
filters, and live reservation updates. FastAPI~[1] validates every request with Pydantic models
(price, category, token), generates OpenAPI documentation used for API testing, and supports
asynchronous calls, so a slow LLM request does not block other users. MySQL~8~[5] provides
built-in FULLTEXT search~[6], which avoids running a separate search service, and transactional
conditional updates for the version-based inventory check. JWT tokens keep authentication
stateless~[4]. The AI description feature calls the OpenAI API~[8]; it needs an API key kept in an
environment variable and has a small per-request cost, which the fallback text limits. Redis would be
added only if time allows, to cache search results.

  \item[US-1 Search and filter.] As a buyer, I want to search by keyword and filter by category and price so I only see relevant items.\\

\subsection*{Data and Safeguards}
All inputs are validated by Pydantic (price $>$ 0, category from an allowed list, valid JWT);
invalid input returns 422. Seller routes check that the user's role is seller, and buyers can confirm
only their own reservations. Passwords are stored as bcrypt hashes, and the JWT signing key and
LLM API key are kept in environment variables, never in the repository. If the LLM API times out
or returns an error, the description endpoint catches the exception and returns a plain fallback string
so the seller's flow is not blocked.

\subsection*{Technical Depth}
\textbf{Search ranking.} Search goes beyond a simple keyword match. Each result is scored on three
things: how well the listing text matches the query (MySQL full-text relevance~[6]), how recently the
listing was posted, and how close its price is to the prices the user has viewed before. The three
scores are combined and results are sorted from highest to lowest.

\textbf{Recommendations.} When a user views a listing, it is saved to their view history. The
recommendation engine represents listing titles and descriptions as TF-IDF vectors~[2], compares the
user's viewed listings with all other active listings by cosine similarity, and returns the 5 most
similar ones.

\subsection*{Evaluation Metrics}
\textbf{E1 -- Search latency:} Send 200 search requests, 50 at a time, against 500 listings.
Target: the 95th percentile is under 300\,ms. Repeat 5 times and report the median of the five runs.

\textbf{E2 -- Recommendation quality:} Create 20 test users who each like one topic and have
viewed a few items in it. Count how many of each user's top 5 recommendations match their topic,
and compare with 5 random items. Target: on average at least 1.5 of 5 match (30\%), clearly above
random, whose expected match rate equals the share of seed listings in the user's topic (reported
alongside the result). The real result is reported even if the target is missed.

\textbf{E3 -- No oversell:} 5 buyers try to reserve each of 10 listings (quantity = 1 each) at the same
time. Target: every item is reserved at most once.

\textbf{Reproducibility:} All tests run in Docker Compose. A SQL file pre-loads fixed test data, and
results are saved to \texttt{/eval/results/}.

\section{Critical Design Decision}
\subsection*{How to Handle Two Buyers Reserving the Same Item}
\begin{itemize}
  \item \textbf{Version-based check (chosen):} the reservation update includes a check on the item's
  version number. If another buyer reserved it first, the version has changed, the update affects no
  rows, and the second request gets a 409. No waiting is needed.
  \item \textbf{Row lock:} lock the database row before reading (\texttt{SELECT \ldots{} FOR UPDATE}~[7]),
  then update. Other requests wait in line until the lock is released.
\end{itemize}

\textbf{Choice: version-based check.} For a campus marketplace, most items have only a few buyers
trying at the same time. The version-based approach has less overhead: requests never wait on a lock
or hold a database connection while waiting, and a conflict is reported immediately as a 409. Test T1
and metric E3 directly verify this behavior.

\textbf{Tradeoff.} If a very popular item gets many requests at once, the version check rejects many
of them and users see many errors. This also happens when quantity is greater than 1: two buyers
who could both be served may still conflict on the version, so the loser must retry. A row lock would
be better in that case.

\textbf{When I would switch:} if load testing shows more than 20\% of requests for a popular listing
failing, I would switch that endpoint to a row lock.

\textbf{AI note:} Claude suggested a row lock as the default. After comparing MySQL's locking
reads~[7] with a version check for this workload, I chose the version-based approach because it
never makes requests wait. A suggestion to use Redis as the primary inventory store was also
rejected, since it would split inventory across two data stores.

\subsection*{Risks}
\textbf{Risk 1 -- Too many 409s under load:} if many users try to reserve a popular item at once,
the version check may reject many requests. \emph{Fallback:} add a short automatic retry on the
client side; if the failure rate exceeds 20\% in testing, switch to a row lock.

\textbf{Risk 2 -- Recommendations not better than random:} TF-IDF similarity may not beat a
random list on a small dataset. \emph{Fallback:} add a simple category-match boost and report both
results.
